# W10 手順5 検証記録（PR本文貼り付け用）

検証日：2026年11月16日（日本時間）

以下はすべて実際のHTTPリクエストとPostgreSQLの照会結果である。予想値やSQLiteの結果は含めていない。

## 検証環境・方法

- Dockerの専用内部ネットワークに、一時的なアプリとPostgreSQLコンテナを作成した。
- PostgreSQL 18.6、トランザクション分離レベルは READ COMMITTED。
- 検証用DB名は `w10_step5`。開発用PostgreSQLとは別のサーバー・DB・ユーザーで、開発用ボリュームのマウントや開発ネットワークへの接続は行っていない。
- 開発用DBからはテーブル定義だけを読み取り専用で複製。既存データは持ち込まず、検証専用の管理者2人、学生4人、授業2件を作成した。外部キーとユーザー・授業の複合一意制約も残した。
- 元の `src/.env` は読まず、コピーもしなかった。アプリの必要なコードをコピーし、守りを外す変更と待機処理はそのコピーだけに加えた。
- 実際の `/login` でログインし、CookieとCSRFトークンを使用してGET・POSTを送った。学生の取り消しはPOSTに `_method=DELETE` を指定した。
- POSTは `Accept: application/json` で送った。そのため、バリデーション違反は422のJSONとして観測している。成功時はControllerの302リダイレクトを追跡せずに記録した。
- PHP組み込みHTTPサーバーを `PHP_CLI_SERVER_WORKERS=4` で動かした。HTTPクライアントも分離環境内で実行し、同時承認には別々の管理者ログインセッションと別々のTCP接続を使用した。
- 各ケースの前に検証用DBの初期状態を作り直した。守りなし／ありで初期条件をそろえた。

## ① 管理者以外を止める

守りなしでは、検証用コピーの `can:decide-enrollments` ミドルウェアと `AdminEntryController` 内の管理者チェックを両方外した。`auth` とCSRFの保護は残した。

| 操作 | 守りなしの実測 | 守りありの実測 |
|---|---|---|
| 一般学生で `GET /admin/entries` | HTTP 200。管理者の申請一覧を取得できた | HTTP 403 |
| 一般学生で `POST /admin/entries/3/approve` | HTTP 302。対象が `pending` から `approved` に変わり、決定日時も保存された | HTTP 403。対象は `pending` のまま、決定日時はNULL |

## ② 状態の移り方

守りなしでは、次のアプリ側チェックを検証用コピーだけから外した。

- 承認時の `status === 'pending'` の確認。
- 取り消しDELETEの `status = 'pending'` 条件。所有者の条件は残した。
- 再申請を事前に止める `Rule::unique(...)`。DBの一意制約は残した。

| 操作 | 守りなしの実測 | 守りありの実測 |
|---|---|---|
| 却下済み申請を管理者が承認 | HTTP 302。`rejected` が `approved` に変わった | HTTP 403。`rejected` のまま |
| 承認済み申請を所有者の学生が取り消す | HTTP 302。対象行が削除された | HTTP 403。`approved` の行が残った |
| 却下された同じ授業に同じ学生が再申請 | HTTP 500。PostgreSQLの `SQLSTATE[23505]`（`timetable_entries_user_id_course_id_unique` 違反）が発生。行は増えず、却下済み1件のまま | HTTP 422。「この授業はすでに登録されています。」を返した。却下済み1件のまま |

再申請については「守りを外すと再申請に成功した」という結果ではない。アプリの事前確認がないためDB制約にぶつかり、500になったことを実際のLaravelログでも確認した。

## ③ 同時の承認

SE300の定員を3人に設定し、承認済み2人・申請中2人の状態から開始した。2人の管理者が異なる2件の申請に対して承認POSTを同時に送った。

両条件ともトランザクション、状態チェック、定員チェックを残した。人数確認と定員チェックの後、保存直前に `sleep(3)` を検証用コピーだけに追加した。ロックなしでは授業・申請の `lockForUpdate()` を両方外し、ロックありでは両方残した。

| 条件 | 2リクエストのHTTP結果 | 最終的な承認済み人数 | 申請中だった2件の最終状態 |
|---|---|---:|---|
| ロックなし | 302 / 302 | **4人（定員超過）** | 両方 `approved` |
| ロックあり | 302 / 422 | **3人（定員内）** | 1件 `approved`、1件 `pending` |

観測ログでも次を確認した。

- ロックなし：別PHPワーカー（PID 33 / 32）が、約0.011秒差で両方「承認済み2人」と数えた。約3秒後に両方保存された。
- ロックあり：最初のワーカー（PID 1）が2人と数えた。次のワーカー（PID 31）は約3.018秒後に3人と数え、満員として422になった。
- 各ケースの最終人数は、HTTPレスポンスだけで判断せず検証用PostgreSQLへのSELECTで確認した。

人数確認SQL：

```sql
SELECT count(*)
FROM timetable_entries
WHERE course_id = 1 AND status = 'approved';
```

`course_id = 1` は、この検証DB内のSE300である。

## 影響・後片付け・未検証事項

- 要求された12ケースはすべて実行できた。未実行の要求項目はない。
- 同時承認はロックなし／あり各1回の実測であり、長時間の負荷試験やすべての割り込み順序を網羅した試験ではない。
- 初回はホストから一時HTTPサーバーに接続できず、ケース実行前に停止した。その一時環境を削除し、HTTPクライアントを検証コンテナ内で動かす方法に変えて全ケースを完了した。
- 元のアプリソースのSHA-256一覧を前後で比較し、一致した。
- 開発用DBの主要7テーブル（users、courses、timetable_entries、reviews、tags、course_tag、favorite_courses）の件数・内容ハッシュを読み取り専用SQLで前後に取得し、一致した。
- 終了後、今回作成した検証用アプリ・PostgreSQLコンテナと専用ネットワークを削除した。検証DBは一時領域に置き、開発用ボリュームには触れていない。
- `sleep()` や守りを外したコードは元の `src/` に加えていない。比較用コピーは `.verification/w10-step5/variants/` にだけ保存している。
